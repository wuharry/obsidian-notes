# B009 第一章線索備援盤點（Three Clue Rule）

[bug 表](../BUGS.md)｜[判定原則](../判定原則與參考.md)｜[測試索引](../README.md)

> 2026-09-07 盤點，對象是 `ai-wrapper/apps/trpg-server/src/data/scenarios/emberCrown/chapters/ch1MistCreek/`。
> 這是**設計缺口清單**，不是引擎 bug 清單 —— 補備援幾乎都是寫劇本，不是改引擎（見最後一節）。

---

## 一句話結論

**門是備援的，脊椎不是。**

三個分支的入口都正確地做了冗餘（`shadow_hand_introduced` 3 個寫入點、`knows_the_altar_binds_a_guardian` 3 個、
`knows_eleanors_dream` 2 個、`caspar_commission_known` 2 個），但每個分支內部的必要結論幾乎都只有一條路。

## 硬違規

| 必要結論 | 獨立路徑 | 問題 |
| --- | --- | --- |
| **通往第二章** | **1** | `scene_mine_aftermath` 是唯一通往第二章的場景，入口條件是 `entity_downed obj_worm_mother`。`entity_downed` 純粹由累積傷害 vs 韌性計算，**任何線索、談判、儀式或 flag 都無法滿足** |

而且宣傳中的非戰鬥解法是死路:`clue_reason_with_her`（hard 檢定，且其前置 `knows_shard_controls_her` 只有一個寫入點）
成功後給 6 個行動的 `withdrawn` 並設 `reasoned_with_her` —— **這個 flag 在第一到四章沒有任何地方讀取**。

## 違規

- **`herbs_done` / `spring_done` 各只有一個寫入點**（`clue_gather_herbs` / `clue_cleanse_spring`），
  兩者都要成功檢定，且**都沒有 `designedDifficulty`** → DC 由 DM 模型每次重猜。
  對照:蜘蛛任務做對了 —— `spiders_done` 有三個寫入點（燒網／查豎井／打巢）。
- **酒館一燒，三個交任務線索死兩個**:`clue_turn_in_spiders` 與 `clue_turn_in_spring` 都掛在酒館的 `npc_rennick`，
  而 `UNLESS_TAVERN_BURNED` 會移除他 → `spiders_done` 可以永遠為真卻無法兌換成 `quest_*_complete`。
  `NpcDefinition.essential` 救不了 —— 它只擋 AI 驅動的離場，不擋作者自己的 `when`。
- **聲望階梯（10/20/30）整條塌成一條路**:+10 只有三個來源（三個交任務線索），
  所以 `rep >= 30`（`scene_mine_crisis` 自動出口）要求三個支線全完成 = 三條單寫入鏈的 AND。
  更糟:`quest_missing_miners.completionFlag` 是 `null` → `resolveQuestStatus` 永遠回 `active` →
  一旦設了 `accepted_quest_mine`，`canAcceptQuest` 擋掉所有支線 → **主線與聲望階梯互斥**。
  而且單一次燒毀（−30）就會讓聲望掉到公告欄 −20 的關閉門檻以下，永久斷掉階梯。
- **`clue_harold_joins` 一次定生死**:唯一寫入 `harold_joined` 的來源，hard 檢定，
  `onFailed` 設 `harold_refused_to_return` 而它自己的條件又擋這個 flag。
  `harold_joined` 是第四章 `flags_set_at_least value 3` 所數的五個 `ALLY_FLAGS` 之一 →
  **第一章擲爛一次 hard，第四章的盟友需求就無聲少掉 20%，全劇本沒有補救路徑**。
- **`mine_door_open` 名義上三條、實際上一條**:
  `clue_door_runes` 需要 `can_read_ancient_script`（只能靠建角選 `origin_scholar` 取得）；
  `clue_door_passphrase` 需要 `clue_ballad_passphrase`（本身又是無 `designedDifficulty` 的檢定，
  且卡在單寫入 flag `shared_story_with_lyon`，來源 `npc_lyon` 刻意沒標 essential）。
  → 對大多數角色只有 `clue_door_forced` 一條，而它也沒有 `designedDifficulty`。

## 一個容易被誤判的陷阱

`read_mine_notice` **名義上有六個寫入點**，看起來很安全。但六個全部落在
`obj_notice_board`、`npc_margret`、`npc_rennick` —— 全在 `scene_silver_hoof_tavern`，
全帶同一個 `UNLESS_TAVERN_BURNED` 條件。**一個玩家行動就同時抹掉六條。**

作者發現了，但補的是一個特製的 fallback 旅行選項（`scenes.ts:320-328`），不是獨立線索來源。

> **教訓:備援稽核不能只數寫入點，要數「不同的存在體與它們的存在條件」。**

## 單向門（不是 Three Clue Rule，但同樣是不可逆）

- `scene_mine_entrance` 是純結局場景，`choice_return` 沒有 `toSceneId` →
  走到礦坑再選「回鎮上」= 直接終局。
- `scene_mine_aftermath` 沒有任何旅行選項 → 只在 `scene_mine_chamber` 拿得到的
  `altar_cleansed` / `saved_the_miner` / `took_the_shard` / `shard_is_the_leash` 一離開就永久失去。

## 引擎能力 vs 缺的東西

**資料模型沒有「必要結論」或「備援線索來源」的概念。** `ClueDefinition` 沒有任何欄位表達
「這條線索是通往結論 X 的 N 條路之一」；冗餘只在「兩條線索剛好 `set_flag` 同一個字串」時隱性存在。

所以:

- **補備援 = 純寫劇本**（多寫一個 `ClueDefinition`，換 `sourceId`／`discoveryHint`，`onRevealed` 設同一個 flag，
  再把 id 加進場景的 `clueIds`）。**零引擎改動。**
- **缺的是稽核，不是能力。** 而稽核很便宜:`integrity.ts` 已經有
  flag → 寫入點 map（`collectWrittenFlags`）與 flag → 讀取點 map（`collectReadFlags`），
  「每個被 `SceneExit.when` / `SceneTravelOption.when` / `EndingChoice.when` 讀取的 flag 至少要有 2 個寫入點」
  只是在既有資料上加幾行。
  ⚠️ 這必須是**新的檢查** —— 現有兩個檢查是「讀了沒人寫」（defect）與「寫了沒人讀」（warning），
  兩個都看不到「剛好只有一個寫入點」。

## 附帶發現:13 / 21 個檢定線索沒有 designedDifficulty

第一章 21 個需要檢定的線索裡有 13 個沒有 `designedDifficulty` → DC 由 DM 模型每次重猜。
`types.ts:415` 本來就建議每個 `requiresSuccessfulCheck` 線索都要標，工作樹的 dmService 提示詞
也已經寫了「設計好的線索門檻仍由引擎驗證」—— 但**那個引擎保證只對真的帶了欄位的線索存在**。

對單路徑的必要結論（`clue_gather_herbs`、`clue_cleanse_spring`、`clue_door_forced`）來說，
沒釘住的 DC 就是「可重試的減速丘」與「看起來像死路」之間的差別。
